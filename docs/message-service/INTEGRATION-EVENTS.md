# Integration events and authoritative eligibility

Actual producer writes were inspected, not inferred from `EVENT_PATTERNS`. Sources: Bidding `apps/bidding-service/src/bids/bids.service.ts`, Order `apps/order-service/src/{service-requests/service-requests.service.ts,orders/orders.service.ts}`, publishers `common/outbox/` in each service, and shared `libs/common/src/{events,outbox}`. Paths below are relative to `backend/`. `bid.created` and `bid.accepted` appearing in the central constants are **not** the admission signal for current bidding writes.

## Existing committed events to consume in Phase 2

All below use eventVersion 1, an outbox UUID as `eventId` and durable producer outbox writes. Producer publishes after transaction commit. The shared `DomainEvent<T>` carries `eventId,eventVersion,occurredAt,producer,data`; RabbitMQ routing pattern carries event name. `occurredAt` is a Date in producer TypeScript and serialized ISO string on the wire. The Order publisher can supply extra transport metadata. Existing payloads do not uniformly contain correlation IDs or monotonic aggregate versions; consumers must tolerate that and use `eventId` as fallback correlation. **Do not require absent fields to accept legitimate v1 events.**

| Pattern                     | Producer → consumer | Actual data relevant to Message                                                                                                                    | Effect                                                                                   |
| --------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `bid.submitted`             | Bidding → Message   | `bidId,biddingRoundId,serviceRequestId,requestId,customerId:null                                                                                   | UUID,workerId,amount,message,validUntil:null                                             | timestamp,submittedAt`                                                                    | invalidate/reconcile; submission row and outbox created in same transaction with `status:active`; authority still required       |
| `bid.revised`               | Bidding → Message   | same IDs, nullable customer; `revisionNo,previousAmount,newAmount,previousMessage,newMessage,version,validUntil,revisedAt`                         | refresh authority; not a new conversation                                                |
| `bid.withdrawn`             | Bidding → Message   | same IDs, nullable customer; `reason:null                                                                                                          | string,version,withdrawnAt`                                                              | immediately mark send snapshot read-only; reconcile authority                             |
| `service_request.cancelled` | Order → Message     | `serviceRequestId,requestId,requestCode,customerUserId,cancelledAt`                                                                                | close sends for request, retain READ                                                     |
| `order.created`             | Order → Message     | `orderId,orderCode,serviceRequestId,requestId,bookingProposalId,customerUserId,customerId,workerUserId,workerId,selectionSource,selectedBidId:null | UUID,selectedMatchResultId:null                                                          | UUID,serviceId,agreedPrice,currency,scheduledAt,addressText,latitude,longitude,createdAt` | authoritative committed selection/conversion signal; reconcile selected worker, link order to same conversation and close others |
| `order.status.changed`      | Order → Message     | `orderId,customerId,customerUserId,workerId,workerUserId,previousStatus,nextStatus,notificationKind`, plus transition-specific fields              | reconcile current order state                                                            |

| `order.cancelled`           | Order → Message     | `orderId,orderCode,customerUserId,customerId,workerUserId,workerId,cancelledByUserId,cancelReason,cancelledAt`                                     | close sends; retain READ                                                                 |

`order.created` is emitted when the worker accepts a booking proposal and Order creates the order/converts the request atomically. Proposal creation is tentative, so neither `booking_proposal.created` nor a mobile selection flag grants selected-worker access. Bidding later consumes `order.created` to select/reject bids. Order can select via recommendation with no bid; strict Phase 1 policy denies that pair unless a valid persisted bid exists. Do not delete losing bids or conversations; Bidding retains bids/revisions. Event `customerId:null` is possible in Bidding and must be resolved through Order, never trusted as missing ownership permission.

Identity suspension/deletion: subscribe to existing `user.suspended`/`user.deleted` only after confirming producer payload at integration time; account/session online verification remains mandatory. Do not invent a revocation guarantee from event names alone.

## Admission authority: proposed Phase 2 internal HTTP contracts

Existing `GET /internal/bids/:bidId/eligibility` (controller route is `internal/bids/:bidId/eligibility`) is designed for Order admission, requires `requestId` and `workerId`, and only accepts active bids. It cannot support selected-order continuity alone. Existing Order `GET /internal/service-requests/:id/bidding-eligibility` returns request ownership/status for bidding, not the selected order snapshot. No existing endpoint is silently changed in Phase 1.

Add these authenticated service-only read contracts in Phase 2; portable response types are `ChatBidAuthority` and `ChatRequestAuthority`:

- `GET /internal/bids/{bidId}/chat-eligibility`: `{bidId,requestId,workerId,status:active|withdrawn|expired|selected|rejected,version,submittedAt,validUntil:null|timestamp,roundStatus,eligible:boolean,verifiedAt}`. Read committed Bidding records, never mobile claims. The response computes eligible from active status, nonexpired validUntil (null means no deadline) and roundStatus != cancelled, matching the existing eligibility logic. Does not declare a selected order valid by itself.
- `GET /internal/service-requests/{requestId}/chat-state`: `{requestId,customerId,status,version,order:null|{orderId,workerId,status,version,completedAt:null|timestamp},verifiedAt}` from the Order-owned database in one consistent snapshot. Do not pass arbitrary customer/worker IDs to this operation.

Both use the existing success/error HTTP envelope. UUID and ISO timestamps are required; versions are nonnegative safe integers (where repository version exists) and monotonic within their own aggregate only. For an Order model without a persisted order version, Phase 2 must add an authoritative monotonic revision or return a documented immutable snapshot token before consumers depend on that value. Do not synthesize revisions from wall-clock time. 404 means no authority record and denies creation/sending; 401/403 indicates service authentication failure; 503 means timeout/dependency unavailable and denies new writes. Internal responses must never be forwarded verbatim to a mobile caller.

Current policy input `ChatEligibilitySnapshot` is built server-side from those responses, local immutable conversation membership, Auth active/session check and configured completion window. Validate request ID and bid worker against the existing conversation and ensure Order ownership matches customer ID. `bidCurrentlyValid` is server-built from Bidding eligible=true, status=active, noncanceled round and validUntil still in the future at write admission; validUntil is checked again using server time after provider/authority I/O. An active database row alone is insufficient. For selected-order continuity a committed order for that same worker plus its persisted active/selected bid establishes the historical valid submission; the former bid deadline does not end the selected conversation, including while Bidding has not yet consumed order.created. Withdrawn/expired/rejected bid records remain read-only pending authoritative reconciliation. `selectedWorkerId` derives only from Order's committed order. `verified` is true only for the current successful online checks. `conversationExists` comes from Message DB; `userActive` comes from authenticated identity; neither is accepted from a client. CREATE checks on every call; SEND and typing check on every event. READ uses immutable local participant membership and active identity, allowing historical access even if upstream eligibility is unavailable.

Use a total authority deadline of 2 seconds with individual requests bounded by the remaining deadline; failure yields ELIGIBILITY_UNAVAILABLE. Avoid retries inside a send transaction. Never hold a database lock while waiting for external HTTP/provider calls. Recheck local lifecycle invalidation generation in the persistence transaction; a concurrent closing event forces retry/revalidation. No distributed transaction exists across Bidding, Order and Message: authorization is current as of online authority reads, with a residual race for a concurrent upstream cancellation after the read. This is explicit, not a claim of linearizable cross-service authorization. A stronger guarantee would require owner-issued permits/atomic fencing across services, deferred unless product requires it. Existing APIs are not sufficient for that guarantee.

## Duplicate/out-of-order consumption

Treat events as invalidation/reconciliation triggers, not permanent authorization grants. On a closing event, conservatively set relevant conversations READ_ONLY immediately in the same transaction as durable consumed-event marker. On any reopening signal, fetch current Bidding/Order authority, validate identity bindings, then update status/order link. A late `bid.submitted` can never reopen canceled request or nonselected worker because current Order snapshot dominates. Do not compare Bidding version to Order version. Unknown order-to-request link requires authoritative lookup; do not drop a cancellation merely because order.created arrived later. Retry unresolved reconciliation and periodically reconcile read-only/current conversations to heal lost events.

Persist consumer inbox dedupe by `(consumer,eventId)` or a Message-only eventId unique table in the same transaction as local updates. Duplicate event ACKs after transaction succeeds. No state mutation then ACK on malformed/unsupported payload: dead-letter permanent failures with redacted metadata. Transient HTTP/DB/broker failure NACK/requeue with bounded exponential backoff+jitter, beginning 1 second, capped 60 seconds, 10 attempts then DLQ and alert; manual replay preserves eventId. Existing shared context/publisher/outbox abstractions are reused by Phase 2 adapters. There is no ordering assumption across queues or producers, and no exactly-once broker claim. Correlation uses inbound request ID when provided, otherwise eventId; logs contain IDs and outcome only.

## Proposed `message.created` v1 (not yet published or registered)

Producer Message → Notification; RabbitMQ pattern `message.created`. Payload uses existing DomainEvent envelope and explicit additive fields:

```ts
{
  eventId: UUID, eventType: 'message.created', eventVersion: 1,
  producer: 'message-service', occurredAt: ISO8601, correlationId: UUID,
  data: { messageId, conversationId, requestId, orderId: UUID | null,
          senderId, recipientId, sequence: DecimalString, messageType: 'TEXT'|'IMAGE'|'VIDEO' }
}
```

This exact shared interface is `MessageCreatedEvent`. Do not include text, raw media URLs, access tokens, phone numbers or credentials. One event/outbox row is created in the same transaction as a new message; `eventId` remains stable across publisher retries. Dedupe notification key `message.created:{messageId}:{recipientId}`. Consumer verifies recipient belongs to the conversation using trusted source data or Message internal verification, respects notification preferences and uses generic “New message” text. Notification currently allowlists event types and categories; adding `message.created` plus chat category/deep-link handling is a Phase 2 task, not an already functioning consumer.

Outbox publisher must mark published only after broker confirmation; a crash after broker delivery may repeat. Backoff/DLQ policy above applies. Notification retries cannot resend or duplicate durable messages. Socket broadcast does not wait for RabbitMQ; if crash occurs after commit and before broadcast, REST history and same-key ACK retry repair the gap. Outbox notification is durable eventual communication, not a promise of durable Socket.IO fanout.
