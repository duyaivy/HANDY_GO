## Findings

1. **Medium — provider-confirmed bytes ignore lower configured upload caps.** `backend/libs/cloudinary/src/cloudinary.service.ts:296` checks the fixed chat caps of 10/100 MiB only. The upload initializer enforces configured caps against client-declared `fileSize`, which cannot prove actual bytes uploaded directly. If video configuration permits 50 MiB, a client may declare a small size, upload 75 MiB and obtain a successful receipt because provider verification permits 100 MiB. Phase 1 explicitly requires the lower of existing upload and chat limits. Compare provider `asset.bytes` against `Math.min(chatCap, configuredImageOrVideoCap)`; reject invalid/nonpositive configured limits; add a regression with declared size below configured cap and provider bytes above it.

2. **Medium — extra-field rejection test uses a stricter pipe than actual startup.** `backend/apps/order-service/src/internal/chat-endpoints.spec.ts:81` enables `forbidNonWhitelisted:true`; actual shared bootstrap at `backend/libs/common/src/bootstrap.ts:42` only enables `whitelist:true`. Thus the test/report claim that forged additional identity fields are rejected does not establish real startup behavior; the real route silently strips them. This does not let a forged sender override the selected authenticated identity, but it violates the strict input contract and makes the recorded evidence inaccurate. Validate raw request keys in a guard before global pipes, or use an unknown/Object parameter with explicit strict DTO parsing (the global pipe will skip the Object metatype). A controller-level pipe on the existing typed parameter alone runs after global stripping and cannot detect removed fields. Cover new Auth/media bodies and the Bidding lookup query if its complete query is intended to be strict. Test with the same global pipe as startup; avoid broadening existing services' shared validation as an unrelated change.

## Notification integration failure assessment

Coordinator observed 217 passing and 8 failing tests with real disposable PostgreSQL/RabbitMQ; the new `message.created` route test passed. These failures must remain visible in final verification. Source inspection supports the following classification:

- Four legacy-notification read/list/count checks are affected by the existing JSON `NOT payload.inAppVisible=false` filter in `notifications.repository.ts:51`, also repeated in count/detail/mark-all. SQL null/missing-path behavior excludes legacy rows whose payload does not set `inAppVisible`. The new Message processor explicitly stores a boolean. This is a pre-existing compatibility defect, not evidence that `message.created` rows fail; cover missing/JSON-null/SQL-null payloads before changing the filter.
- Two device tests expect cross-user registration of the same token to conflict, while current `devices.repository.ts:37` explicitly retires the old record, cancels its queued attempts and rebinds the physical token. Current Push worker independently checks recipient ownership before delivery. These tests conflict with existing deliberate shared-device behavior. Resolve the policy/fixture discrepancy explicitly instead of weakening ownership guards to make them green.
- Swagger operation-count test expects nine operations at `notification.integration.spec.ts:170`, whereas existing admin broadcast adds a tenth. Verify the intended operation set rather than merely changing a count. This is unrelated to the added Message event.
- The optional-opt-out event test counts all durable rows at `events.integration.spec.ts:255`; current push integration may persist an `inAppVisible:false` row for a push-eligible recipient. Assert visible in-app records and push work separately. An opt-out from in-app does not imply a push opt-out.

The bullets explain overlapping symptoms and are not a replacement for the coordinator's exact eight failing assertion list. No new-source High severity finding was inferred solely from legacy red tests.

## Positive review evidence and limits

- Session lookup binds live unrevoked/unexpired session, account and marketplace user; strict active/provisioned User Trust status uses a bounded RxJS timeout. No positive authority cache was introduced.
- Authority snapshots read actual owned records and persisted versions; Order uses repeatable-read for request/order. Internal service credentials use timing-safe checks. New pair lookup avoids cross-service table access or unnecessary Message schema changes.
- New uploads use authenticated provider type, no overwrite, random exact keys and HMAC owner/key/resource binding persisted in provider context. Verification independently retrieves actual provider type/format/bytes and rejects public/foreign/forged references. Private download URLs expire within five minutes. This supports the intended design but provider tests use SDK doubles: live image/video completion and private URL playback remain NOT_RUN.
- Notification allowlists trusted Message producer/version, validates message-specific identifiers/sequence/type, strips body/URL fields, uses generic Vietnamese text, routes only the supplied authoritative recipient and stores conversation deep links. Logical deduplication key is message+recipient and persists inside the existing inbox/effects transaction. Default production in-app/push policies are optional. Explicit simulated development policies still classify Message as mandatory; this must not be used as evidence of real preference behavior.
- Recipient trust assumes the existing authenticated broker/service trust boundary. No separate Message recipient-verification HTTP route or per-publisher broker credential proof was demonstrated. Phase 3 must enforce the broker permissions described in the handoff; a producer-name string alone is not cryptographic publisher identity.
- HMAC receipts depend on the current Cloudinary API secret. Rotation can make existing receipts unverifiable; the implementation report records this. Plan bounded old-secret verification or a migration before rotation.
- No proof was available of real Cloudinary private access, Auth/User Trust/Bidding/Order databases running together, or FCM delivery to devices. Those gaps must not be labeled PASS from these unit/HTTP-controller tests.
