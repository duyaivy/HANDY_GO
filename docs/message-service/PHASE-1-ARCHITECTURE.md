## Existing integration and infrastructure conventions

`backend/libs/common/src/events/domain-event.ts` defines eventId/eventVersion/occurredAt/producer/data. `event-patterns.ts` is a registry, not proof a producer exists. Shared `outbox/outbox-publisher.service.ts` publishes stable IDs with routing type/source/producer and payload/data aliases, up to five attempts and DLQ handling. Order also has its own publisher. Notification validates explicit producer/version/payload allowlists in `apps/notification-service/src/events/event-contracts.ts`; `message.created` is currently unsupported. Its consumer and `event-topology.ts` implement confirmed retry/DLQ transfers (2/10/30 seconds) before acknowledging. Reuse these patterns.

Existing common success/error envelope is `{statusCode,message,data,code?}` (`libs/common/src/dto/api-response.dto.ts`); errors require code. Bootstrap and ValidationPipe are centralized (`libs/common/src/bootstrap.ts`). Pino and secret redaction live in `libs/logger`. Tests use Vitest/SWC and shared alias configuration (`backend/vitest.config.ts`); no existing chat contract suite exists.

Gateway routes come from `backend/apps/api-gateway/src/proxy/proxy.constants.ts`; no Message route is configured. Existing Bidding SSE `/api/v1/bids/requests/:requestId/events` emits lightweight invalidation, including access for eligible workers without bids. Its membership cannot authorize chat. Mobile SSE client is `mobile/src/services/sse/bidding-sse-client.ts`.

## Decision

1. **Boundary:** Message owns pairwise conversation history, ordered messages, attachment references, two read cursors and notification outbox. Order owns request/customer/selection/order lifecycle; Bidding owns committed bid eligibility; Auth/User Trust own identity/status. Message does not import another service implementation or query its tables.
2. **Database:** independent Prisma client and migration directory under `backend/foundations/message-service/prisma`; explicit `message` schema for tables/enums and `_prisma_migrations` selected with `?schema=message`. No cross-service FKs. Reuse PostgreSQL infrastructure. Use isolated local DB for proof. Production schema/role provisioning is deferred, with grants described in DATABASE-DESIGN.md; runtime role must not access other schemas. No changes to existing migration histories or aggregate production migration command. The staged foundation lives outside `backend/apps` because production migration inventory scans that directory for deployable services. Keeping it under `foundations` preserves the existing production inventory without registering or provisioning an unfinished runtime. This location has the same directory depth, preserving shared migration helper and generated-client paths.
3. **Creation:** authenticated bidId is the only creation selector. Server loads committed bid and authoritative request owner, verifies requester is that worker/customer, immutable participants and valid eligibility. Unique request/customer/worker constraint returns the existing conversation on retries. Retain customerId for indexed listings and historical authorization.
4. **Lifecycle:** valid bid creates access; withdrawal/cancellation disables sending; order creation links the selected worker's existing conversation without moving history, closes competitors. Historical participant reads remain possible. Completed order defaults to read-only (configurable future grace, default zero). Transitions never delete history.
5. **Authority:** prefer synchronous authenticated internal Bidding+Order chat authorization snapshots for CREATE/SEND and ephemeral events; missing, stale or unavailable authority denies writes/joins. Existing endpoints are insufficient for selected continuity. Events invalidate caches and trigger reconciliation, not sole permission grants. Snapshot interfaces are Phase 1 contracts, Phase 2 producer work. No long-lived positive authorization cache. Distributed snapshot/write races remain: define authorization at the last authority check immediately preceding persistence, with later event reconciliation; stronger atomic cross-service revocation would require a separate protocol and is not claimed.
6. **Realtime:** Socket.IO on transport path `/api/v1/chat/socket.io/`, default namespace `/`, user/conversation rooms. Keep SSE for bidding. Persist transaction before ACK/broadcast; bigint sequence + REST resync are durable truth. Socket.IO does not guarantee exactly-once delivery. RabbitMQ handles lifecycle and notifications, not typing or every socket broadcast.
7. **Reliability:** serialize sequence allocation per conversation; transactional message+attachment+outbox; sender-scoped client UUID for retries; outbox/inbox dedup and retry/DLQ. Events can duplicate/reorder; reconcile current authority instead of blindly applying arrival order. No Redis dependency for one instance.
8. **Media:** reuse Gateway/Cloudinary. Never trust arbitrary URL/publicId or submitted MIME/size. Phase 2 must bind completed uploads to user and chat intent, verify provider metadata, and authorize delivery. Existing public media cannot be represented as private; private delivery needs provider configuration and authenticated resolver with short-lived URLs, not a new provider. Binary payloads never traverse chat sockets.
9. **Scaling:** one instance initially. Later add Redis Socket.IO adapter and shared ephemeral typing/rate limits, sticky polling sessions or websocket-only transport, and revocation propagation. PostgreSQL remains durable. Do not shard/partition preemptively.

## Alternatives and conflicts

A separate PostgreSQL database is operationally valid but unnecessary given the observed schema-per-service topology; use it if production privileges cannot isolate `message`. Existing SSE cannot supply bidirectional send/ACK/typing semantics. Pure event projection would reduce synchronous dependencies but is unsafe for timely revocation without freshness guarantees; deny while projection unconfirmed or stale.

Order supports `WorkerSelectionSource.recommendation` and nullable selectedBidId. The approved strict prior-bid requirement wins: a recommendation worker without a previously valid bid gets no chat even when selected. Product policy can change later, explicitly; Phase 1 does not silently make that exception.

Current internal bid eligibility endpoint accepts active only; current Order bidding eligibility omits selected/order state. Reusing them unchanged would break selected-worker continuity. Current uploads have no private ownership proof. Both gaps are explicit Phase 2 integration dependencies, not completed runtime features.
