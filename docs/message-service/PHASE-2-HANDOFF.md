# Phase 2 handoff

Phase 1 supplies the database foundation, portable contracts, checked API description, policy helpers and executable verification. It does not supply a running HTTP server, Socket.IO gateway, producer endpoints, upload ownership ledger, notification binding or mobile UI. Do not expose the proposed routes until Phase 2 security and integration acceptance checks pass. Phase 3 alone owns public Nginx/proxy/VPS rollout.

## Parallel execution and mocks

Backend foundation/persistence, internal authority endpoints, media security prerequisites, and Mobile list/conversation/reply screens can start concurrently with ownership separated by directories. Mobile copies or consumes the portable Message contracts only, never Nest/Prisma runtime code. The source of truth is `backend/libs/common/src/message-contracts/index.ts` and `openapi.json` in this directory; do not create competing hand-written wire formats.

Mocks use fixed valid UUIDs, ISO UTC timestamps, decimal-string sequences and the exact shared success/error envelopes. Model no-bid denial, two workers with isolated rooms, read-only withdrawal, selected continuation, expired token, generic dependency-unavailable error, duplicate ACK, duplicate broadcast, lost ACK, paginated gap recovery and unavailable reply preview. Media mocks use independently verified fixtures explicitly marked as test data; a mocked publicId is not proof of real upload ownership. Socket mock ACK only after adding a message to its history fixture. Never treat mock success as runtime integration evidence.

Persistence/authority/media and real Socket.IO tests must converge before Backend/Mobile integration is accepted. Notification producer and consumer ship as a coordinated contract change. Phase 3 routing is a separate dependency; local clients can target the local Message instance directly while preserving the specified transport path.

## Runtime acceptance tests still required in Phase 2

- Two concurrent real send requests with same client key commit once; mismatched retries conflict; failed transaction emits no event/ACK.
- Nonparticipants fail REST reads, socket join/send/read/typing, including a worker who bid on the same request; forged sender or user header fails.
- Authority becomes withdrawn/canceled during a live socket: subsequent sends and ephemeral updates fail and room access is removed; stale events never reopen access.
- Selected worker retains conversation/history; competitors become read-only; recommendation without prior valid bid denies creation.
- Internal HTTP refuses unauthenticated caller; trust secret is never accepted from public mobile traffic; token expiry disconnect and revocation policy tested.
- Uploaded asset belongs to another user, is uncompleted/public/oversized or metadata lies: rejected; private media resolver denies nonparticipant, refreshes expired URLs.
- Cross-conversation reply, attachment mismatch, read cursor regression and missing cursor targets fail at runtime and DB boundaries.
- Socket outage/broadcast loss recovers through REST; notification broker retry/DLQ preserves event ID and deduplicates recipient notification.
- Run actual gateway/Nginx path and transport compatibility only in Phase 3 staging; never infer production readiness from Phase 1.

## Provisioning decisions

The Prisma foundation is staged at `backend/foundations/message-service/prisma`, outside the production inventory's `backend/apps` scan. When runtime and infrastructure work is authorized, coordinate any relocation into `backend/apps/message-service` with service registration, migration inventory, explicit Message script/config/test paths and documentation updates. Preserve the independent migration history and generated-client/helper resolution; adding a directory under `apps` alone is insufficient. Phase 1 does not authorize that relocation or production registration.

Verify intended production PostgreSQL endpoint supports schema-level isolation and least-privilege migration/runtime roles. Provision `message` without modifying another history; never point the disposable test runner at existing data. Configure explicit MESSAGE database overrides/direct URL before any controlled migration. Confirm private Cloudinary delivery and deletion/retention policy; completion grace defaults to zero pending product change. None of these steps is a production deployment authorization.
